# ランキングAPI負荷試験結果

## 実施概要

- 実施日: 2026-08-12
- 試験ツール: k6（Dockerイメージ `grafana/k6:latest`）
- 対象API: `GET /rankings/players?top=10`
- 接続先: Docker Compose内の `http://api:8080`

## 試験環境

### EC2

| 項目 | 値 |
| --- | --- |
| リージョン | ap-northeast-1（東京） |
| インスタンスタイプ | t3.micro |
| vCPU | 2 |
| メモリ | 1 GiB |
| ルートEBS | 8 GiB |

### コンテナ構成

同じEC2上のDocker Composeで、負荷を送る側と受ける側を同居させて実行した。

| サービス | イメージまたは役割 |
| --- | --- |
| api | ASP.NET Core / .NET 10 API |
| db | `postgres:16` |
| redis | `redis:7-alpine` |
| k6 | `grafana/k6:latest` |

## 試験条件

- 仮想ユーザー数（VU）は、10 / 100 / 500 / 1000 の順で試験した。
- 30秒で指定VUまで増加し、1分間維持した後、30秒で0 VUまで減少させた。
- 各VUは1リクエストごとに1秒待機した。
- ランキング取得のみを対象とし、ゲームデータを更新するAPIは実行していない。
- APIの構造化ログ出力も有効な状態で測定した。

### 成功基準

| 指標 | 基準 |
| --- | --- |
| HTTP失敗率 | 1%未満 |
| 応答時間 | p95が500ms未満 |
| checks成功率 | 99%超 |

`checks` では、HTTPステータスが200であることと、レスポンスに`rankings`配列が含まれることを確認した。

## 結果

| 最大VU | HTTPリクエスト数 | p95応答時間 | 最大応答時間 | HTTP失敗率 | checks成功率 | 判定 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 10 | 918 | 3.08ms | 558.59ms | 0.00% | 100.00% | 合格 |
| 100 | 9,044 | 2.56ms | 70.69ms | 0.00% | 100.00% | 合格 |
| 500 | 24,783 | 1.61秒 | 48.58秒 | 0.00% | 100.00% | p95超過 |
| 1000 | 5,981 | 5.14秒 | 1分50秒 | 0.93% | 99.06% | p95超過 |

### 1000 VU時の補足

- 56件のHTTPリクエストがタイムアウトした。
- HTTP失敗率0.93%とchecks成功率99.06%は、今回の基準内だった。
- k6設定上の最大VUは1000だったが、実際に観測された同時実行VUの最大値は920だった。
- 試験終了時に318件の実行中イテレーションが中断された。
- 試験後、api、db、redisコンテナはすべて起動を維持し、Redisはhealthyだった。

## 解釈

この結果は、ランキングAPIだけの性能ではなく、1 GiBのEC2内で以下を同居実行した構成の結果である。

```text
k6 + API + PostgreSQL + Redis + 構造化ログ出力
```

100 VUまでは成功基準を満たした。500 VUからp95応答時間が基準を超え、1000 VUではタイムアウトも発生した。一方で、試験後も常駐コンテナは停止していない。

外部クライアントからの実際の利用性能を測定する場合は、k6を別EC2などで実行し、API・DB・Redisと負荷生成処理を分離して再測定する必要がある。

## 再実行コマンド

API・PostgreSQL・Redisを通常起動した状態で、EC2上から実行する。

```bash
docker compose run --rm -e VUS=100 -e DURATION=1m k6
docker compose run --rm -e VUS=500 -e DURATION=1m k6
docker compose run --rm -e VUS=1000 -e DURATION=1m k6
```

試験中は別ターミナルで`docker stats`を実行し、API・DB・Redis・k6のCPUとメモリ使用量を確認する。
